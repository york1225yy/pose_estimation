## 1. 可用骨骼关键点检测算法总览

按检测范式分为三类：**Top-Down（先检测人体框再估计关键点）**、**Bottom-Up（先检测关键点再组合）**、**单阶段端到端**。车载驾驶员场景只有单人，Top-Down 或单阶段最适合。

### 1.1 Top-Down 方法

| 算法 | 机构 | PyTorch 支持 | 论文/代码 |
|------|------|-------------|-----------|
| **SimpleBaseline** | MSRA (2018) | ✅ 官方 | ECCV 2018 |
| **HRNet** | MSRA (2019) | ✅ 官方 | CVPR 2019 |
| **LiteHRNet** | MSRA (2021) | ✅ MMPose | arXiv 2021 |
| **RTMPose** | 商汤/OpenMMLab (2023) | ✅ MMPose | arXiv 2023 |
| **ViTPose** | 港大 (2022) | ✅ 官方 | NeurIPS 2022 |
| **SimCC** | 浙大 (2022) | ✅ MMPose | ECCV 2022 |
| **DWPose** | 阿里/S-Lab (2023) | ✅ | arXiv 2023 |

### 1.2 Bottom-Up 方法

| 算法 | 机构 | PyTorch 支持 | 说明 |
|------|------|-------------|------|
| **OpenPose** | CMU (2017) | ✅ | 经典 PAF 方法，VGG-19骨干，多人场景强 |
| **Lightweight OpenPose** | Intel/Osokin (2019) | ✅ 官方PyTorch | MobileNetV1骨干，CPU实时，COCO 18关键点 |
| **HigherHRNet** | MSRA (2020) | ✅ MMPose | 多尺度，精度高 |
| **DEKR** | MSRA (2021) | ✅ | 解耦关键点回归 |

> **关于 Lightweight OpenPose**：即 Daniil-Osokin（Intel）的 [lightweight-human-pose-estimation.pytorch](https://github.com/Daniil-Osokin/lightweight-human-pose-estimation.pytorch)，是 OpenPose 的轻量化工业落地版本，在嵌入式/CPU 场景中被广泛使用，值得重点评估。

### 1.3 单阶段端到端（最适合车端实时部署）

| 算法 | 机构 | PyTorch 支持 | 说明 |
|------|------|-------------|------|
| **YOLOv5-Pose** | Ultralytics 社区 (2022) | ✅ 社区分支 | 最早 YOLO 姿态分支，非官方正式版 |
| **YOLOv7-Pose** | Wang et al. (2022) | ✅ 官方 | 学术界高精度版本，E-ELAN 骨干 |
| **YOLOv8-Pose** | Ultralytics (2023) | ✅ 官方 | 首个 Ultralytics 官方 Pose，工业成熟 |
| **YOLO11-Pose** | Ultralytics (2024) | ✅ 官方 | C3k2 骨干，同精度参数量减少 ~10% |
| **YOLO12-Pose** | Ultralytics (2025) | ✅ 官方 | R-ELAN + 注意力机制，大模型精度领先 |
| **YOLO-NAS-Pose** | Deci AI (2023) | ✅ | 神经架构搜索优化，量化友好 |
| **BlazePose (MediaPipe)** | Google (2020) | ✅（第三方） | 移动端极轻量 |
| **MoveNet** | Google (2021) | ✅（ONNX转换） | Lightning/Thunder 两版本 |
| **RTMDet-Pose** | 商汤 (2023) | ✅ MMPose | RTMDet骨干+RTMPose头 |

## 附录：YOLO Pose 各版本专项对比

> Ultralytics 官方文档：https://docs.ultralytics.com/tasks/pose/

### A.1 各版本架构演进脉络

```
YOLOv5-Pose (社区, 2022)
    └── 非官方分支，将检测头扩展为关键点回归，不稳定，不建议新项目使用

YOLOv7-Pose (Wang et al., 2022)
    └── 学术版本，E-ELAN骨干，高精度(AP 67.2)但参数量极大(121M)
        适合作为精度上限参考，不适合车端

YOLOv8-Pose (Ultralytics, 2023)
    └── 首个官方 Ultralytics Pose，C2f骨干，解耦检测头
        5档(n/s/m/l/x)，工业生态最成熟

YOLO11-Pose (Ultralytics, 2024)
    └── C3k2骨干替代C2f，引入CBAM注意力，同精度参数减少~10%
        FLOPs显著降低，是YOLOv8直接升级版

YOLO12-Pose (Ultralytics, 2025)
    └── 引入R-ELAN(残差高效层聚合)+ 区域注意力(A2模块)
        中大型档位精度领先，小型档位与YOLO11持平
        适合对精度要求更高的场景
```

### A.8 YOLO11 vs YOLO12 选型决策指南

```
选 YOLO11-pose 的情况：
  ✅ 需要成熟稳定的生态（更多部署案例、Issue 解答）
  ✅ TDA4 TIDL 工具链已有 YOLO11 适配脚本
  ✅ 对最新版本持保守态度，优先稳定性
  ✅ 团队有 YOLO11 Fine-tune 经验
  → 推荐档位：YOLO11s-pose（9.9M / 23.4G / AP 62.0）

选 YOLO12-pose 的情况：
  ✅ 新项目，不依赖历史代码
  ✅ 驾驶场景中遮挡关键点（髋部等）检测精度要求高
  ✅ 相同参数量预算下需要更低的 GFLOPs（利于 TDA4 功耗优化）
  ✅ 可接受较新版本的少量 Bug 风险
  → 推荐档位：YOLO12s-pose（9.8M / 20.5G / AP 63.4）

两者均不选的情况：
  ❌ 需要关键点精度 AP > 70 → 改用 RTMPose-m（AP 75.3）
  ❌ 需要极致轻量（< 5M 参数）→ 改用 LiteHRNet-18 或 RTMPose-tiny
```

### A.9 车端输入分辨率裁剪对 YOLO 的影响

驾驶场景固定 ROI 后，可将输入从 640×640 缩小，GFLOPs 与推理延迟成比例下降：

| 输入尺寸 | GFLOPs (YOLO11s) | 相对 640×640 | 预估 TDA4 延迟 | AP 损失 |
|---------|-----------------|-------------|--------------|-------|
| 640×640 | 23.4 | 100% | ~28ms | 基准 |
| 480×480 | 13.2 | 56% | ~16ms | -1.0 AP |
| **384×384** | **8.4** | **36%** | **~10ms** | **-1.5 AP** |
| 320×320 | 5.8 | 25% | ~7ms | -2.5 AP |

> **推荐**：YOLO11s/12s-pose 搭配 **384×384** 输入，TDA4 端延迟 ~10ms，系统总帧率可达 50+ FPS。

### 4.2 各模型详细分析

#### RTMPose（强烈推荐 ⭐⭐⭐⭐⭐）

**优势：**
- OpenMMLab 生态，PyTorch 原生，支持完整训练/微调流程
- 基于 SimCC 坐标分类头，消除 Heatmap 的量化精度损失，INT8 量化友好
- 提供 tiny/s/m/l 多档位，灵活选择精度-速度平衡点
- 已在多个工业嵌入式平台（RKNN、NCNN、ONNXRuntime）验证
- 支持 `mmpose` 直接导出 ONNX，流程标准化

**劣势：**
- 依赖 MMPose 框架，环境配置略复杂（但文档完善）
- 需要先用目标检测器获取人体框（Top-Down 两阶段）

**推荐配置：** `RTMDet-nano（检测）+ RTMPose-s（姿态）`

---

#### YOLOv8-Pose / YOLO11-Pose（推荐 ⭐⭐⭐⭐）

**优势：**
- 单阶段端到端，检测+姿态联合推理，部署极简
- Ultralytics 生态完善，一行代码导出 ONNX/TorchScript/TFLite
- 支持直接 `model.export(format='onnx')` + TDA4 TIDL 工具链
- 社区生态最活跃，Issue 响应快
- 天然支持多人同时检测

**劣势：**
- 关键点精度（COCO AP Pose 60-65）略低于 RTMPose（71+）
- 640×640 输入时 GFLOPs 偏高，需裁剪输入尺寸降低计算量
- 关键点头部与检测头耦合，自定义修改关键点数量成本较高

**推荐配置：** `YOLO11s-pose（9.9M，23.4G）`，输入裁剪至 384×384

---

#### LiteHRNet（轻量极限场景推荐 ⭐⭐⭐⭐）

**优势：**
- 参数量极小（1.1M），计算量最低（0.2G），最适合算力受限平台
- 保留 HRNet 高分辨率表示能力，精度超出参数量预期
- 适合 TDA4 C7x DSP 侧推理

**劣势：**
- 精度（AP 64.8）在所有关键点准确时可接受，但遮挡场景较弱
- 需搭配单独目标检测器（两阶段），增加整体延迟

---

#### HRNet（高精度参考基线 ⭐⭐⭐）

**优势：**
- 姿态估计领域经典基线，精度天花板（AP 74-75）
- 论文、代码成熟，方便学术对比

**劣势：**
- **参数量大（28-64M），计算量高，TDA4 实时推理压力大**
- 不推荐车端直接部署，建议作为离线精度上限参考

---

#### BlazePose / MoveNet（移动端参考 ⭐⭐⭐）

**优势：**
- 参数量极小，ARM CPU 上实时运行（30+ FPS）
- BlazePose 提供 33 个关键点，包含更丰富的上半身信息

**劣势：**
- PyTorch 原生支持差（主要是 TFLite/TensorFlow 生态），迁移成本高
- Backbone 专为移动端 CPU 优化，TDA4 MMA 加速优化收益不如标准卷积

---

#### OpenPose（不推荐用于车端 ⭐⭐）

**原理**：CMU 提出的经典 Bottom-Up 方法，使用 **Part Affinity Fields（PAF）** 编码肢体连接关系，先检测所有关键点热图，再通过二分图匹配组装骨骼。

**关键点体系**：COCO 18 关键点（比 COCO 17 多一个中颈点 `neck`，实际更方便躯干角度计算）。

**优势：**
- 多人场景鲁棒性极强，学术界最成熟的基线之一
- 提供完整 PyTorch 实现，社区资料极为丰富
- 对复杂遮挡场景有一定的 PAF 关联容错能力

**劣势（车端部署的根本问题）：**
- **骨干网络过重**：原版使用 VGG-19（~200M 参数，~160 GFLOPs），TDA4 根本无法实时运行
- **PAF 后处理无法硬件加速**：二分图匹配（匈牙利算法）必须在 ARM CPU 上运行，延迟随人数增加，调试复杂
- **单人场景资源浪费**：驾驶员场景只有 1 人，Bottom-Up 的组装开销完全是冗余计算
- **量化不友好**：PAF 热图的多尺度特征图对 INT8 量化敏感，精度损失较大

**结论**：**不推荐用于 TDA4 车端部署**，可作为离线数据标注辅助工具使用。

---

#### Lightweight OpenPose（有限推荐 ⭐⭐⭐）

**来源**：Intel 工程师 Daniil-Osokin 的 [lightweight-human-pose-estimation.pytorch](https://github.com/Daniil-Osokin/lightweight-human-pose-estimation.pytorch)，是面向工业落地的 OpenPose 轻量化版本。

**核心改进**：将 VGG-19 骨干替换为 **MobileNetV1**，并大幅缩减 PAF 分支的卷积深度，实现在 Intel CPU 上 ~33 FPS 的实时推理。

**参数与性能**：~4.1M 参数，~9 GFLOPs，COCO AP ≈ 56，CPU 实时。

**优势：**
- 参数量小（4.1M），显著优于原版 OpenPose
- PyTorch 原生实现，训练/微调流程清晰
- 在 ARM CPU（如 A72）上可达 10~20 FPS，无需 NPU 支持
- 适合作为**纯 CPU 降级方案**（当 TDA4 NPU 资源被其他任务占用时）
- COCO 18 关键点带有 `neck` 点，躯干角度计算比 COCO 17 更直接

**劣势：**
- **PAF 后处理问题依然存在**：与 OpenPose 同根，后处理步骤复杂，约占总延迟的 30~40%
- **精度低于同量级 Top-Down 模型**：COCO AP ≈ 56，明显低于 RTMPose-s（71.2）和 LiteHRNet-18（64.8）
- **MobileNetV1 骨干老旧**：深度可分离卷积在 TDA4 MMA 上的并行效率不如标准卷积，加速比不理想
- **ONNX 导出有坑**：PAF 解码部分含有动态尺寸操作，需手动拆分模型（骨干+头部导出为 ONNX，后处理用 C++ 重写）
- **驾驶场景遮挡适应差**：下半身被方向盘遮挡时，PAF 关联容易将无效关键点错误连接

**TDA4 部署可行性评估**：

| 步骤 | 可行性 | 说明 |
|------|--------|------|
| 骨干网络 ONNX 导出 | ✅ 可行 | MobileNetV1 + PAF 预测头可正常导出 |
| TIDL INT8 编译 | ⚠️ 有风险 | 需替换不支持算子，建议 FP16 编译 |
| PAF 后处理 | ⚠️ CPU 运行 | 只能跑在 ARM A72，延迟约 8~15ms |
| 总体实时性 | ⚠️ 勉强 | 骨干 ~12ms + 后处理 ~12ms ≈ 24ms，约 40 FPS，余量不足 |

**结论**：Lightweight OpenPose 在**资源极度受限且无法使用 MMPose 生态**的情况下可作为备选，但综合精度、部署复杂度和 TDA4 适配性来看，**不如 LiteHRNet-18 或 RTMPose-tiny**。如果团队对 Lightweight OpenPose 熟悉，可以用于快速原型验证，最终量产建议迁移到 RTMPose。

## 5. 坐姿识别技术路线建议

### 5.1 两种技术路线对比

#### 路线 A：端到端分类（直接训练坐姿分类器）

```
输入图像 → 姿态特征提取 → 全连接分类头 → 坐姿类别
```

| 维度 | 评估 |
|------|------|
| 训练数据需求 | ❌ 需要大量有标注坐姿样本（每类 ≥500 张） |
| 泛化能力 | ❌ 对驾驶员体型、座椅角度变化敏感 |
| 可解释性 | ❌ 黑盒，调试困难 |
| 修改坐姿定义 | ❌ 需重新训练 |
| 精度上限 | ✅ 端到端训练理论精度高 |

#### 路线 B：关键点检测 + 规则引擎（推荐 ✅）

```
输入图像 → 骨骼关键点检测 → 角度/距离特征计算 → 规则引擎 → 坐姿类别
```

| 维度 | 评估 |
|------|------|
| 训练数据需求 | ✅ 只需关键点标注，无需坐姿类别标注 |
| 泛化能力 | ✅ 角度/比例特征天然对尺度、体型不敏感 |
| 可解释性 | ✅ 每条规则对应明确的生物力学含义 |
| 修改坐姿定义 | ✅ 只需修改阈值或新增规则，无需重训 |
| 阈值调整 | ✅ 可根据实车标定快速调整 |
| 遮挡处理 | ✅ 低置信度关键点可跳过对应规则 |

#### 路线 C：关键点 + 轻量分类器（Hybrid，增强方案）

```
关键点坐标 + 角度特征 → SVM / XGBoost / 轻量MLP → 坐姿类别
```

> 在规则引擎基础上，可用少量标注数据（每类 50~100 张）训练轻量分类器，作为规则边界的数据驱动补充。

### 5.2 推荐路线决策

> **核心结论：推荐路线 B（关键点 + 规则引擎）为主，路线 C 为辅。**

**推荐理由：**

1. **数据效率最优**：关键点标注（COCO/VehiclePose 格式）可复用公开数据集，远比人工标注 10 类坐姿样本高效
2. **符合工程标准**：规则可直接映射人机工程学标准（ISO 11429、GB/T 15243），方便 ADAS 系统集成与审核
3. **运行时零成本**：规则计算为 O(n) 运算（n=关键点数量≈17），不增加推理延迟
4. **坐姿定义天然规则化**：题目中 10 类坐姿均有明确角度/距离约束，如"头前倾 > 25°"直接对应关键点几何量，无需学习

**不建议路线 A 的根本原因：**
- 10 类坐姿的类内差异大（不同体型在同一姿势下形体差异显著），类间边界模糊（如"轻微前倾"与"严重前倾"的图像差异很小），用端到端分类器很难学到明确的类别边界，而规则引擎可以精确控制这个边界。

## 6. 10类坐姿的关键点规则定义

### 6.1 核心几何量定义

```python
import numpy as np

# COCO 17 关键点索引
NOSE = 0
L_EAR, R_EAR = 3, 4
L_SHOULDER, R_SHOULDER = 5, 6
L_ELBOW, R_ELBOW = 7, 8
L_WRIST, R_WRIST = 9, 10
L_HIP, R_HIP = 11, 12

def angle_2d(v1: np.ndarray, v2: np.ndarray) -> float:
    """计算两个二维向量的夹角（度），范围 [0, 180]"""
    cos_a = np.dot(v1, v2) / (np.linalg.norm(v1) * np.linalg.norm(v2) + 1e-6)
    return float(np.degrees(np.arccos(np.clip(cos_a, -1.0, 1.0))))

# 图像坐标系中的竖直向上方向（Y轴向下，所以向上为负Y）
VERTICAL_UP = np.array([0.0, -1.0])
HORIZONTAL   = np.array([1.0,  0.0])
```

### 6.2 各坐姿规则实现

```python
def classify_posture(kp: np.ndarray, conf: np.ndarray,
                     seat_back_angle: float = None) -> tuple[str, dict]:
    """
    驾驶员坐姿分类规则引擎

    参数
    ----
    kp   : shape (17, 2)，COCO 17 关键点像素坐标 (x, y)
    conf : shape (17,)，各关键点置信度 [0, 1]
    seat_back_angle : 靠背角度传感器读数（度），可选

    返回
    ----
    posture_label : str，输出坐姿标签
    evidence      : dict，触发规则的具体数值（调试用）
    """
    CONF_THR = 0.4

    def valid(*idxs) -> bool:
        return all(conf[i] > CONF_THR for i in idxs)

    # ── 基础几何点 ────────────────────────────────────────────
    neck     = (kp[L_SHOULDER] + kp[R_SHOULDER]) / 2.0   # 颈根（双肩中点）
    mid_hip  = (kp[L_HIP]      + kp[R_HIP])      / 2.0   # 髋部中点
    mid_ear  = (kp[L_EAR]      + kp[R_EAR])      / 2.0   # 头部代理（双耳中点）

    # ── 各轴向量 ──────────────────────────────────────────────
    trunk_vec = neck    - mid_hip   # 躯干轴：髋 → 肩
    neck_vec  = mid_ear - neck      # 颈轴：  肩 → 耳

    # ── 计算核心角度 ──────────────────────────────────────────
    # 1. 躯干前倾角（躯干轴与竖直轴夹角）
    trunk_tilt = angle_2d(trunk_vec, VERTICAL_UP)
    # 判断前倾还是后仰：躯干向量 Y 分量正值(向下)→ 后仰
    trunk_backward = trunk_vec[1] > 0

    # 2. 头前倾角（颈轴相对躯干轴的前倾偏转）
    head_fwd = angle_2d(neck_vec, trunk_vec)

    # 3. 头侧倾角（双耳连线与水平线夹角的余角）
    if valid(L_EAR, R_EAR):
        ear_vec   = kp[L_EAR] - kp[R_EAR]
        head_side = 90.0 - angle_2d(ear_vec, HORIZONTAL)
    else:
        head_side = 0.0

    # 4. 躯干旋转角（由双肩投影宽度估算）
    shoulder_dist_2d = abs(kp[L_SHOULDER][0] - kp[R_SHOULDER][0])   # 像素宽
    shoulder_dist_3d = np.linalg.norm(kp[L_SHOULDER] - kp[R_SHOULDER])  # 欧氏距
    trunk_rotate = float(np.degrees(
        np.arccos(np.clip(shoulder_dist_2d / (shoulder_dist_3d + 1e-6), 0.0, 1.0))
    ))

    # 5. 单侧肩膀抬起量（归一化到双肩距离）
    shoulder_lift_norm = (abs(kp[L_SHOULDER][1] - kp[R_SHOULDER][1])
                          / (shoulder_dist_3d + 1e-6))

    # 6. 手臂抬起（肘部 Y 低于肩部 Y 表示抬起，图像Y轴向下）
    l_arm_up = valid(L_ELBOW, L_SHOULDER) and kp[L_ELBOW][1] < kp[L_SHOULDER][1]
    r_arm_up = valid(R_ELBOW, R_SHOULDER) and kp[R_ELBOW][1] < kp[R_SHOULDER][1]
    arm_raised = l_arm_up or r_arm_up

    evidence = {
        "trunk_tilt":          round(trunk_tilt, 2),
        "trunk_backward":      trunk_backward,
        "head_fwd":            round(head_fwd, 2),
        "head_side":           round(head_side, 2),
        "trunk_rotate":        round(trunk_rotate, 2),
        "shoulder_lift_norm":  round(shoulder_lift_norm, 3),
        "arm_raised":          arm_raised,
        "seat_back_angle":     seat_back_angle,
    }

    # ══════════════════════════════════════════════════════════
    # 规则引擎（优先级从高到低，先匹配先返回）
    # ══════════════════════════════════════════════════════════

    # ─────────────────────────────────────────────────────────
    # 规则 1：睡姿
    #   头大幅度侧倾 > 35°（靠窗）
    # ─────────────────────────────────────────────────────────
    if valid(L_EAR, R_EAR) and head_side > 35:
        return "睡姿", evidence

    # ─────────────────────────────────────────────────────────
    # 规则 2：半躺休息 / 斜躺副驾
    #   靠背传感器 ≥ 120°，或躯干后仰角 > 35°
    # ─────────────────────────────────────────────────────────
    reclined = (seat_back_angle is not None and seat_back_angle >= 120) or \
               (trunk_backward and trunk_tilt > 35)
    if reclined and valid(L_SHOULDER, R_SHOULDER, L_HIP, R_HIP):
        # 身体向中控台（右）侧倾 → 斜躺副驾
        # 驾驶员坐左侧，右肩Y更低（下沉）说明向副驾侧倾
        lateral_lean = (kp[R_SHOULDER][1] - kp[L_SHOULDER][1]) / (shoulder_dist_3d + 1e-6)
        if lateral_lean > 0.15:
            return "斜躺副驾", evidence
        return "半躺休息", evidence

    # ─────────────────────────────────────────────────────────
    # 规则 3：侧身取物
    #   躯干旋转 > 15° 且单侧肩膀抬高 > 20%
    # ─────────────────────────────────────────────────────────
    if valid(L_SHOULDER, R_SHOULDER) and trunk_rotate > 15 and shoulder_lift_norm > 0.20:
        return "侧身取物", evidence

    # ─────────────────────────────────────────────────────────
    # 规则 4：低头玩手机
    #   头前倾 > 25°（颈椎折痕明显）
    # ─────────────────────────────────────────────────────────
    if valid(NOSE, L_SHOULDER, R_SHOULDER) and head_fwd > 25:
        return "低头玩手机", evidence

    # ─────────────────────────────────────────────────────────
    # 规则 5：严重前倾
    #   躯干前倾角 > 20°（背部离靠背 > 8cm）
    # ─────────────────────────────────────────────────────────
    if (valid(L_SHOULDER, R_SHOULDER, L_HIP, R_HIP)
            and not trunk_backward and trunk_tilt > 20):
        return "严重前倾", evidence

    # ─────────────────────────────────────────────────────────
    # 规则 6：轻微前倾
    #   躯干前倾角 8°~20°（肩胛骨离靠背 3-8cm）
    # ─────────────────────────────────────────────────────────
    if (valid(L_SHOULDER, R_SHOULDER, L_HIP, R_HIP)
            and not trunk_backward and 8 < trunk_tilt <= 20):
        return "轻微前倾", evidence

    # ─────────────────────────────────────────────────────────
    # 规则 7：直立办公
    #   背挺直（前倾 < 5°）且手臂抬起
    # ─────────────────────────────────────────────────────────
    if trunk_tilt < 5 and arm_raised:
        return "直立办公", evidence

    # ─────────────────────────────────────────────────────────
    # 规则 8：后仰放松
    #   头后仰 10°~25°，躯干基本直立（<8°）
    # ─────────────────────────────────────────────────────────
    if valid(NOSE, L_EAR, R_EAR, L_SHOULDER, R_SHOULDER):
        head_backward_angle = angle_2d(neck_vec, -trunk_vec)
        if 10 <= head_backward_angle <= 25 and trunk_tilt < 8:
            return "后仰放松", evidence

    # ─────────────────────────────────────────────────────────
    # 规则 9（默认）：标准驾驶坐姿
    #   头-颈-肩-髋基本一条直线，所有指标均在正常范围内
    # ─────────────────────────────────────────────────────────
    return "标准驾驶坐姿", evidence
```

### 6.3 规则阈值速查表

| 坐姿 | 主要关键点 | 核心触发条件 | 优先级 |
|------|-----------|-------------|--------|
| 睡姿 | 双耳 | 头侧倾 > 35° | 1（最高） |
| 半躺休息 | 双肩、双髋 + 靠背传感器 | 靠背 ≥ 120° 或躯干后仰 > 35° | 2 |
| 斜躺副驾 | 双肩、双髋 + 靠背传感器 | 靠背 ≥ 120° + 向副驾侧横向倾 > 15% | 2 |
| 侧身取物 | 双肩 | 躯干旋转 > 15° + 单肩高度差 > 20% | 3 |
| 低头玩手机 | 鼻、双耳、双肩 | 头前倾 > 25° | 4 |
| 严重前倾 | 双肩、双髋 | 躯干前倾 > 20° | 5 |
| 轻微前倾 | 双肩、双髋 | 躯干前倾 8°~20° | 6 |
| 直立办公 | 双肩、双肘 | 躯干前倾 < 5° + 单臂抬起 | 7 |
| 后仰放松 | 鼻/耳、双肩 | 头后仰 10°~25° + 躯干直立 < 8° | 8 |
| 标准驾驶坐姿 | — | 默认兜底 | 9（最低） |

> **阈值标定建议**：以上为初始工程参考值，实车标定阶段需采集不同体型驾驶员（身高155~195cm）的实际运动数据，绘制各指标分布直方图，用 ROC 曲线方法确定最优阈值截断点。

## 7. TDA4 部署关键注意事项

### 7.1 TDA4VM 硬件特性

| 处理单元 | 算力 | 推荐用途 |
|---------|------|---------|
| C7x DSP + MMA (Matrix Multiply Accelerator) | ~8 TOPS (INT8) | 深度学习推理主力 |
| MMA 精度支持 | INT8 / FP16 | 卷积、矩阵乘法 |
| ARM Cortex-A72 (quad-core) | 通用处理 | 规则引擎、后处理、系统调度 |
| C66x DSP | 定点信号处理 | 不用于姿态推理 |

### 7.2 模型导出与编译流程

```bash
# Step 1: PyTorch → ONNX（opset 11，静态 shape）
python tools/export_onnx.py \
    --config configs/body_2d_keypoint/rtmpose/coco/rtmpose-s_8xb256-420e_coco-256x192.py \
    --checkpoint rtmpose-s.pth \
    --input-shape 1 3 192 256 \
    --opset 11 \
    --output rtmpose_s.onnx

# Step 2: ONNX 简化（移除冗余节点）
python -m onnxsim rtmpose_s.onnx rtmpose_s_sim.onnx

# Step 3: ONNX → TIDL 格式（TI 工具链）
# 参考 TI EdgeAI-TIDL-Tools
tidl_model_import.py \
    --model_path rtmpose_s_sim.onnx \
    --accuracy_level 1 \          # 1=INT8, 0=FP32
    --calibration_frames 200 \
    --output_dir ./tidl_out/

# Step 4: 性能评估
tidl_benchmark --model tidl_out/ --iterations 500 --warmup 50
```

### 7.3 关键优化策略

| 优化项 | 说明 | 预期收益 |
|--------|------|---------|
| **ROI 裁剪** | 驾驶员位置固定，裁剪左半画面 ROI，分辨率从 640×640 降至 320×256 | FLOPs 减少 ~75% |
| **INT8 量化** | RTMPose SimCC 头无热图，INT8 损失 < 1% AP | 速度提升 ~2x |
| **NHWC 布局** | TDA4 MMA 偏好 NHWC，导出时指定内存排列 | 减少布局转换开销 |
| **算子替换** | `nn.Upsample(bilinear)` → `ConvTranspose2d`（TIDL 不支持双线性插值） | 消除编译报错 |
| **固定 batch=1** | 避免动态 shape 导致 TIDL 编译失败 | 编译稳定性 |
| **跳帧推理** | 姿态网络每 2 帧推理一次（15 FPS 推理），结合卡尔曼滤波平滑 | 算力需求减半 |
| **上半身裁剪** | 只检测躯干以上区域（坐姿场景膝盖以下不可见），输入缩至 192×160 | 进一步降低计算量 |

### 7.4 预期性能指标（TDA4VM，INT8）

| 模型方案 | 输入分辨率 | 精度 (AP≈) | 推理延迟 | 整体帧率 |
|---------|-----------|-----------|---------|---------|
| RTMDet-nano + RTMPose-tiny | 320×256 | ~62 | ~15ms | ~65 FPS |
| **RTMDet-nano + RTMPose-s** | **320×256** | **~68** | **~22ms** | **~45 FPS** ✅ |
| YOLO11s-pose | 384×384 | ~60 | ~28ms | ~35 FPS ✅ |
| LiteHRNet-18（仅姿态） | 192×160 | ~61 | ~8ms | ~100 FPS ✅ |

### 8.1 整体推理架构

```
┌─────────────────────────────────────────────────────────────────┐
│                  Camera Input (30 FPS, 1920×1080)               │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 每帧
                           ▼

└──────────────────────────┬──────────────────────────────────────┘
                           │ 每 2 帧推理一次（姿态网络）
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│         RTMPose-s (TDA4 MMA INT8)                               │
│         推理延迟: ~12ms                                          │
│         输出: 17×2 关键点坐标 + 17 置信度                        │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│         卡尔曼滤波平滑 (ARM A72, ~0.5ms)                         │
│         平滑抖动，保持关键点时序一致性                             │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│         角度/距离特征计算 (ARM A72, ~0.3ms)                      │
│         trunk_tilt, head_fwd, trunk_rotate 等 6 个核心量         │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│         规则引擎分类 (ARM A72, ~0.1ms)                           │

                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│         输出（CAN 总线 / MQTT / HMI 预警）                       │
└─────────────────────────────────────────────────────────────────┘

总端到端延迟: < 20ms | 系统帧率: ≥ 30 FPS ✅
```
